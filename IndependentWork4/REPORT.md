# Самостійна робота №4. Розширення ієрархії та наслідки змін базового класу

## 1. Початкова ієрархія

```
LibraryItem (Title, PublicationYear, virtual DisplayDetails)
├── Book     (+ Author,      override DisplayDetails)
└── Journal  (+ IssueNumber, override DisplayDetails)
```

Спочатку конструктори виглядали так:

```csharp
public LibraryItem(string title, int publicationYear) { ... }

public Book(string title, int publicationYear, string author)
    : base(title, publicationYear) { ... }

public Journal(string title, int publicationYear, int issueNumber)
    : base(title, publicationYear) { ... }
```

## 2. Модифікація базового класу (крок 4)

До `LibraryItem` додано:

```csharp
private readonly string _uniqueId;

public string UniqueId
{
    get { return _uniqueId; }
}

public LibraryItem(string uniqueId, string title, int publicationYear)
{
    _uniqueId = uniqueId;
    _title = title;
    _publicationYear = publicationYear;
}
```

### Які зміни довелося внести в похідні класи

| Клас | Що змінилось |
|---|---|
| `Book` | у конструктор додано параметр `string uniqueId`, виклик `base(title, publicationYear)` замінено на `base(uniqueId, title, publicationYear)` |
| `Journal` | те саме: новий параметр `uniqueId` і новий виклик `base(uniqueId, title, publicationYear)` |
| `Program.Main` | усі місця, де створювались `Book` і `Journal`, отримали додатковий аргумент (`"BK-001"`, `"JR-014"`) |

Метод `DisplayDetails()` у похідних класах **змінювати не довелося**. Вони викликають `base.DisplayDetails()`, а базова реалізація вже виводить `UniqueId`. Властивість `UniqueId` нащадки отримали автоматично.

### Чому це сталося

1. **Конструктори не успадковуються.** Похідний клас зобов'язаний викликати один із конструкторів базового класу (явно через `: base(...)` або неявно конструктор без параметрів). Старого конструктора `LibraryItem(string, int)` більше немає, тому компілятор видає помилку **CS7036**: «There is no argument given that corresponds to the required parameter...» для `Book` і `Journal`.
2. **Ланцюжок залежностей.** Зміна сигнатури базового конструктора «каскадом» розходиться вниз: спочатку на прямих нащадків, потім на код, який їх створює. Якби на той момент вже існував `AudioBook`, його довелося б міняти теж. Це класичний приклад проблеми **крихкого базового класу** (fragile base class).
3. Добре, що поле `_uniqueId` приватне і доступне лише через read-only властивість. Тому нащадки не залежать від внутрішнього зберігання, і змінювати довелося тільки конструктори.

> Як можна було уникнути каскаду: залишити старий конструктор поряд із новим, наприклад `LibraryItem(string title, int year) : this(Guid.NewGuid().ToString("N")[..8], title, year)`, або генерувати ID всередині базового класу. Тоді зміна стала б *розширенням* без порушення сумісності. У завданні ж потрібно саме змінити конструктор, щоб побачити наслідки.

## 3. Розширення ієрархії (крок 5)

```
LibraryItem
├── Book
│   └── AudioBook (+ Narrator)
└── Journal
```

`AudioBook` успадковується від `Book`, бо аудіокнига **є** книгою (has author) і додатково має оповідача. Для цього не довелося змінити **жодного рядка** в існуючих класах. Це і є розширення відповідно до принципу Open/Closed: код відкритий для розширення, але закритий для модифікації.

```csharp
public AudioBook(string uniqueId, string title, int publicationYear, string author, string narrator)
    : base(uniqueId, title, publicationYear, author)
{
    _narrator = narrator;
}

public override void DisplayDetails()
{
    base.DisplayDetails();       // LibraryItem + Book
    Console.WriteLine($"    Формат: аудіокнига, читає: {Narrator}");
}
```

Завдяки ланцюжку `base.DisplayDetails()` кожен рівень додає тільки свою частину інформації, тому дублювання немає.

## 4. Переваги та недоліки наслідування

**Переваги:**
- повторне використання коду: `Title`, `PublicationYear`, `UniqueId` написані один раз;
- поліморфізм: `List<LibraryItem>` обробляє книги, журнали та аудіокниги одним циклом;
- нові типи додаються легко (`AudioBook`), без зміни старого коду.

**Недоліки:**
- **сильне зв'язування**: будь-яка зміна базового класу (особливо конструктора) ламає всіх нащадків;
- ієрархія жорстка. Якщо з'явиться «аудіожурнал» (подкаст), його не можна успадкувати і від `Journal`, і від `AudioBook`, бо в C# немає множинного наслідування класів;
- глибокі ієрархії важко читати: щоб зрозуміти `AudioBook.DisplayDetails()`, треба переглянути три класи.

**Коли наслідування доцільне:** між класами є справжнє відношення «є» (`AudioBook` **є** `Book`), базовий клас стабільний, а нащадки лише уточнюють поведінку.

**Коли воно призводить до проблем, і чим тут краща композиція:** якщо ознаки комбінуються довільно (формат: паперовий / електронний / аудіо; тип: книга / журнал), наслідування дає вибух класів. Краще винести формат в окремий об'єкт:

```csharp
public class LibraryItem
{
    public IMediaFormat Format { get; }   // PaperFormat, AudioFormat(narrator), EbookFormat(fileSize)
}
```

Тоді «аудіожурнал» – це просто `Journal` з `AudioFormat`, без нового класу. Також формат можна змінити під час виконання, чого наслідування не дозволяє.

## 5. Висновок

Модифікація базового класу виявилась «дорожчою», ніж розширення. Зміна одного конструктора змусила правити всіх нащадків і весь код, що їх створює. Додавання `AudioBook` не потребувало жодної правки. Тому базові класи варто проєктувати стабільними, а нові можливості додавати через нових нащадків або через композицію.

## Відповіді на контрольні запитання

1. **Як зміна конструктора базового класу вплинула на похідні класи?** `Book` і `Journal` перестали компілюватися (CS7036), бо викликали неіснуючий тепер `base(title, year)`. Довелося додати параметр `uniqueId` у їхні конструктори та передати його в `base(...)`, а також оновити код у `Main`.
2. **Чим відрізняється розширення ієрархії через новий похідний клас від модифікації наявного базового класу?** Розширення (`AudioBook`) додає новий код і не чіпає старий, тому нічого не ламається. Модифікація базового класу змінює контракт, від якого залежать усі нащадки, і зміни поширюються каскадом.
3. **У яких випадках для цієї задачі композиція могла б бути кращою за наслідування?** Коли ознаки комбінуються (формат × тип видання) або можуть змінюватися під час роботи. Наприклад, формат (`AudioFormat`, `EbookFormat`) як окремий об'єкт усередині `LibraryItem` замість окремих класів `AudioBook`, `AudioJournal`, `EBook`, `EJournal`...
4. **Як поліморфний виклик DisplayDetails() допомагає перевірити правильність ієрархії?** У циклі по `List<LibraryItem>` кожен об'єкт виводить свою інформацію: книга з автором, журнал з номером, аудіокнига з автором *і* оповідачем. Звідси видно, що `override` спрацював і що ланцюжок `base.DisplayDetails()` проходить через усі рівні.
