# Самостійна робота №6. Інтерфейс vs абстрактний клас: практичні критерії

Перед тим як писати код, обидва сценарії зіставлено з таблицею критеріїв з лекції:

| Критерій | Сценарій 1: сповіщення | Сценарій 2: файли |
|---|---|---|
| Чи є спільний **код** (не лише сигнатури)? | ні, кожен канал відправляє по-своєму | так, відкриття й закриття файлу однакові |
| Чи є спільний **стан** (поля)? | ні | так: шлях, вміст, лічильник |
| Чи потрібен фіксований **порядок кроків**? | ні | так: open → process → close |
| Відношення між класами | «вміє надсилати» (can-do) | «є обробником файлів» (is-a) |
| Чи можуть класи мати інших предків / інші ролі? | так (Push ще й логер) | не потрібно |
| **Вибір** | **інтерфейс** | **абстрактний клас** |

---

## Сценарій 1: Система сповіщень

### Обраний підхід: інтерфейс `INotifier`

### Обґрунтування вибору

У цьому сценарії краще використовувати інтерфейс `INotifier`, оскільки:

1. **Немає спільної реалізації.** Email формує тему й тіло листа, SMS обрізає текст до 70 символів, Push будує JSON. Спільна лише *сигнатура* `Send(string message)`, а для опису самої сигнатури призначений саме інтерфейс.
2. **Множинна поведінка.** `PushNotifier` одночасно є і сповіщувачем (`INotifier`), і логером (`ILogger`). Клас може реалізувати скільки завгодно інтерфейсів, але успадкувати лише один базовий клас.
3. **Різні базові типи.** У реальній системі `EmailNotifier` міг би вже успадковуватися від `SmtpClientBase`, а `SmsNotifier` від класу SDK провайдера. Абстрактний клас `NotifierBase` зайняв би єдине місце для наслідування.
4. **Слабке зв'язування (DIP).** Клієнтський код залежить лише від контракту `INotifier`. Новий канал (Telegram, Viber) додається новим класом без змін у старому коді.

**Чому абстрактний клас тут менш доречний:** він був би порожнім (лише `abstract void Send`). Користі від нього немає, а обмеження «один базовий клас» з'являється.

### Реалізація

```csharp
public interface INotifier
{
    string ChannelName { get; }
    void Send(string message);
}

public class SmsNotifier : INotifier
{
    private const int MaxLength = 70;
    private readonly string _phone;
    ...
    public void Send(string message)
    {
        string text = message.Length > MaxLength
            ? message.Substring(0, MaxLength - 3) + "..."
            : message;
        Console.WriteLine($"[SMS]   To: {_phone} ({text.Length} симв.): {text}");
    }
}

public class PushNotifier : INotifier, ILogger { ... }

// Демонстрація в Main
List<INotifier> notifiers = new List<INotifier>
{
    new EmailNotifier("student@rfkit.edu.ua"),
    new SmsNotifier("+380671234567"),
    push
};

foreach (INotifier notifier in notifiers)
{
    notifier.Send(message);
}
```

## Сценарій 2: Обробка файлів

### Обраний підхід: абстрактний клас `FileProcessor`

### Обґрунтування вибору

1. **Спільні кроки.** Відкриття (перевірка існування, читання) і закриття (вивід, очищення) однакові для всіх форматів. В абстрактному класі вони написані **один раз** як приватні методи `Open()` і `Close()`, тому дублювання немає.
2. **Шаблонний метод (Template Method).** Публічний невіртуальний метод `Process()` фіксує порядок `Open → ProcessContent → Close`, а `try/finally` гарантує, що файл буде «закрито» навіть при помилці. Нащадок не може забути закрити файл чи переставити кроки, бо він реалізує лише `ProcessContent`.
3. **Спільний стан.** `FilePath`, `Content`, `_processedCount` – це поля й властивості з рівнем доступу `protected`/`private`. Інтерфейс поля зберігати не може.
4. **Відношення «є».** `XmlFileProcessor` *є* обробником файлів, і жодних інших «ролей» йому не потрібно.

**Чому інтерфейс тут менш доречний:** з інтерфейсом `IFileProcessor` кожен клас мав би сам реалізувати відкриття й закриття. Це дублювання коду, і кожен нащадок міг би зробити це по-різному (або забути `finally`). Default interface methods у C# 8+ частково це вирішують, але вони не можуть зберігати стан і не можуть заборонити перевизначення порядку кроків.

### Реалізація

```csharp
public abstract class FileProcessor
{
    protected string FilePath { get; private set; }
    protected string Content { get; private set; }
    private int _processedCount;

    public abstract string FormatName { get; }

    public void Process(string path)          // шаблонний метод
    {
        Open(path);
        try
        {
            string result = ProcessContent(Content);
            _processedCount++;
            Console.WriteLine($"    Результат: {result}");
        }
        finally
        {
            Close();
        }
    }

    private void Open(string path) { ... }    // спільний крок
    private void Close() { ... }              // спільний крок

    protected abstract string ProcessContent(string content);   // унікальна частина
}

public class XmlFileProcessor : FileProcessor
{
    public override string FormatName => "XML";

    protected override string ProcessContent(string content)
    {
        XDocument doc = XDocument.Parse(content);
        ...
    }
}
```

Реалізації: `TextFileProcessor` (рядки й слова), `XmlFileProcessor` (елементи через `XDocument`), `CsvFileProcessor` (записи й середня оцінка). Тестові файли програма створює сама в папці `samples`.

Демонстрація поліморфізму: колекція з елементами базового типу `FileProcessor`, на кожному викликається `Process(...)`.

## Загальні висновки: практичні критерії вибору

**Обирайте інтерфейс, якщо:**
- потрібно описати *здатність* («вміє надсилати», «можна порівняти», «можна перебрати»);
- реалізації не мають спільного коду;
- клас має поєднувати кілька ролей або вже має базовий клас;
- потрібне слабке зв'язування й легке підставлення моків у тестах.

**Обирайте абстрактний клас, якщо:**
- нащадки мають спільний код і/або спільний стан (поля);
- потрібно зафіксувати алгоритм, а змінювати лише окремі кроки (Template Method);
- потрібні `protected`-члени, конструктор, контроль над тим, що можна перевизначати;
- між класами є чітке відношення «є» в одній ієрархії.

**Комбінований варіант** часто найкращий: інтерфейс як публічний контракт (`IFileProcessor`) плюс абстрактний клас як зручна базова реалізація (`FileProcessorBase : IFileProcessor`). Так зроблено і в самому .NET: `IList<T>` / `Collection<T>`, `IDisposable` / `Stream`.

## Відповіді на контрольні запитання

1. **Які ознаки підказують, що сценарій краще моделювати через інтерфейс?** Реалізації спільні лише сигнатурою, але не кодом. Відношення «вміє» (can-do). Класу потрібно кілька ролей або він уже має предка. Важлива взаємозамінність і тестованість.
2. **У чому перевага абстрактного класу для процесів зі спільними кроками виконання?** Спільні кроки пишуться один раз, а порядок фіксується шаблонним методом (`Process`) і не може бути порушений нащадками. Спільний стан зберігається в полях. Нащадки реалізують тільки свою унікальну частину.
3. **Як порівняння двох підходів допомагає прийняти архітектурне рішення?** Видно ціну кожного варіанту: що доведеться дублювати, які обмеження з'являються (одне наслідування), наскільки сильним буде зв'язування. Рішення спирається на критерії, а не на звичку.
4. **Яку роль у ваших прикладах відіграє поліморфізм?** Клієнтський код працює зі списками `List<INotifier>` і `FileProcessor`. Він викликає `Send` / `Process`, не знаючи конкретних класів, а реалізацію обирає CLR під час виконання. Новий канал чи формат додається без змін у циклі.
