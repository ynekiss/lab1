# Самостійна робота №18

**Тема:** PLINQ: дослідження продуктивності та безпеки.

**Мета:** Порівняти продуктивність PLINQ і звичайного LINQ на різних обсягах даних та дослідити проблеми потокобезпечності при паралельній обробці.

**Хід роботи:**
1. Створив консольний проєкт `IndependentWork12`.
2. Згенерував `List<int>` з випадковими числами (`Random(42)`) розміром 1, 5 і 10 млн елементів.
3. Як обчислювально інтенсивну операцію реалізував перевірку на просте число (`IsPrime`, перебір дільників до √n) і перетворення `ScoreOf` (`Math.Sqrt`, `Math.Log`, `Math.Sin`). Для порівняння додав дешеву операцію `x % 2 == 0`, `x * 2`.
4. Виконав однакові запити через LINQ (`.Where().Select().Sum()`) і PLINQ (`.AsParallel()...`), час виміряв `Stopwatch` (прогрів + середнє з 3 запусків). Окремо перевірив колекцію з 1000 елементів і вплив `WithDegreeOfParallelism`.
5. Створив сценарій з побічними ефектами: `count++`, `sum += x` у `ForAll` і `List<int>.Add` у `Select` без синхронізації, запустив кожен по 5 разів.
6. Виправив проблему чотирма способами: `lock`, `Interlocked`, `ConcurrentBag<int>` і запит без побічних ефектів (`Count()`, `Sum()`, `ToList()`). Також перевірив порядок результатів з `AsOrdered()` і без нього.
7. Описав експерименти, результати й висновки у [REPORT.md](REPORT.md).

**Висновок:** PLINQ вигідний лише для дорогих операцій над великими колекціями: на дорогій операції він майже вдвічі швидший на 2 ядрах, а на дешевій операції чи малій колекції виграшу практично немає. Зміна спільних змінних з PLINQ-запиту щоразу дає неправильний результат, тому агрегувати треба самими операторами PLINQ або через `Interlocked`/`lock`/потокобезпечні колекції.

**Запуск:** `dotnet run -c Release`
