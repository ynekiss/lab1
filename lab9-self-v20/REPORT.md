# Самостійна робота №9. Звіт: делегати й лямбда-вирази у власних утилітах

## Реалізація

```csharp
public static IEnumerable<TResult> Map<TSource, TResult>(IEnumerable<TSource> collection, Func<TSource, TResult> mapper)
{
    var result = new List<TResult>();
    foreach (var item in collection)
    {
        result.Add(mapper(item));
    }
    return result;
}

public static IEnumerable<T> Filter<T>(IEnumerable<T> collection, Predicate<T> predicate)
{
    var result = new List<T>();
    foreach (var item in collection)
    {
        if (predicate(item))
        {
            result.Add(item);
        }
    }
    return result;
}

public static void ForEach<T>(IEnumerable<T> collection, Action<T> action)
{
    foreach (var item in collection)
    {
        action(item);
    }
}
```

`MaxBy` реалізовано за зразком з методички: один прохід, порівняння ключів через `IComparable<TKey>.CompareTo`. Для порожньої колекції він повертає `default(T)`, а при рівних максимумах повертає перший елемент. Усі методи перевіряють аргументи через `ArgumentNullException.ThrowIfNull`.

Демонстрація використовує 4 типи колекцій (`List<Product>`, `List<int>`, `string[]`, `Dictionary<string, int>`) і різні лямбди: проєкції (`p => p.Name`, `n => n * n`, `w => w.ToUpper()`), умови (`p => p.Price > 1000`, `n => n % 2 == 0`), ключі (`p => p.Price`, `n => Math.Abs(n)`, `w => w.Length`) і дії (`p => Console.WriteLine(...)`, `n => sum += n`). Повний вивід програми наведено нижче, у розділі «Запуск і приклад виводу».

## 1. Чому делегати корисні для створення таких утиліт?

Делегат – це тип-посилання на метод, тобто «поведінка як параметр». Утиліта бере на себе **незмінну** частину алгоритму (перебір колекції, накопичення результату, пошук максимуму), а **змінну** частину (що саме перетворити, яку умову перевірити) отримує ззовні через делегат.

Без делегатів довелося б писати окремий метод під кожен випадок: `FilterExpensiveProducts`, `FilterEvenNumbers`, `FilterLongWords`... Кожен з них дублював би той самий цикл `foreach`. З делегатом є один `Filter<T>`, який працює для будь-якого типу й будь-якої умови. Це принцип «відкритий для розширення, закритий для змін»: нова умова не потребує зміни утиліти.

Стандартні делегати `Func<>`, `Action<>`, `Predicate<>` позбавляють потреби оголошувати власні типи делегатів, а їхні назви одразу підказують призначення:
- `Func<T, TResult>` – функція, що повертає значення (перетворення, ключ);
- `Predicate<T>` – умова, що повертає `bool` (по суті `Func<T, bool>`);
- `Action<T>` – дія без результату.

## 2. Як лямбда-вирази спрощують виклик цих методів?

Лямбда дає змогу описати поведінку **прямо в місці виклику**, без окремого іменованого методу:

```csharp
// Без лямбди: окремий метод + передача групи методів
private static bool IsExpensive(Product p) { return p.Price > 1000; }
var expensive = CollectionUtils.Filter(products, IsExpensive);

// З лямбдою: одна читабельна строка
var expensive = CollectionUtils.Filter(products, p => p.Price > 1000);
```

Додаткові переваги:
- **виведення типів:** компілятор сам визначає `TSource`, `TResult`, `T` з колекції та лямбди, тому писати `Map<Product, string>(...)` не потрібно;
- **замикання:** лямбда може використовувати зовнішні змінні. У демонстрації `CollectionUtils.ForEach(numbers, n => sum += n)` накопичує суму в локальній змінній `sum`;
- **делегати як значення:** лямбду можна зберегти у змінну (`Predicate<int> isPositive = n => n > 0;`) і перевикористати в різних викликах.

## 3. Порівняння з вбудованими LINQ-операторами

| Аспект | `CollectionUtils` | LINQ (`System.Linq.Enumerable`) |
|---|---|---|
| Синтаксис виклику | статичний: `CollectionUtils.Filter(list, x => ...)` | методи розширення: `list.Where(x => ...)` – ланцюжок читається зліва направо |
| Виконання | **негайне (eager)**: результат одразу в `List<T>` | **відкладене (lazy)** для `Where`/`Select`: обчислення відбувається під час перебору, через `yield` |
| Пам'ять | створюється проміжний список на кожному кроці | проміжних колекцій немає, елементи «течуть» по конвеєру |
| Тип умови | `Predicate<T>` | `Func<T, bool>`, є перевантаження з індексом `(x, i) => ...` |
| `MaxBy` | повертає `default(T)` для порожньої колекції | для значимих типів кидає `InvalidOperationException`, для посилальних повертає `null`; підтримує `IComparer` |
| Оптимізації | немає | спеціальні шляхи для масивів і `List<T>`, об'єднання `Where().Select()` в один ітератор |
| Можливості | 4 методи | понад 50 операторів, інтеграція з EF Core (`IQueryable`, переклад у SQL) |

Наприкінці програма порівнює результати напряму:

```
CollectionUtils: Ноутбук, Клавіатура, Монітор
LINQ:            Ноутбук, Клавіатура, Монітор
Результати однакові: True
MaxBy однаковий: True
```

**Висновок.** Власні утиліти дають той самий результат і добре показують, як LINQ влаштований усередині: перебір + делегат. Для реальних проєктів LINQ кращий завдяки відкладеному виконанню, оптимізаціям і зручному ланцюжковому синтаксису. Власні методи мають сенс тоді, коли потрібна специфічна поведінка, якої немає в LINQ (наприклад, свій `ForEach` для `IEnumerable<T>`, `MaxBy` зі своєю обробкою порожньої колекції), або для навчання.

## Відповіді на контрольні запитання

1. **Чому делегати є зручним механізмом для передавання поведінки в узагальнені методи?** Узагальнений метод не знає типу елементів, тому не може сам вирішити, як їх перетворювати чи фільтрувати. Делегат дає змогу передати цю логіку ззовні, а цикл і накопичення результату залишаються в одному місці.
2. **У чому різниця між Func<T, TResult>, Action<T> та Predicate<T>?** `Func<T, TResult>` приймає `T` і повертає `TResult` (перетворення, ключ). `Action<T>` приймає `T` і нічого не повертає (дія, вивід). `Predicate<T>` приймає `T` і повертає `bool` (умова; еквівалент `Func<T, bool>`).
3. **Які переваги дає поєднання generic-методів і лямбда-виразів під час роботи з колекціями?** Один метод працює з будь-якими типами (`int`, `string`, `Product`), а поведінка задається короткою лямбдою в місці виклику. Типи компілятор виводить сам і перевіряє на етапі компіляції. Дублювання циклів зникає, а код читається як опис того, *що* зробити, а не *як*.
4. **У яких випадках власні утиліти на кшталт Map чи Filter корисно реалізувати самостійно, навіть якщо існує LINQ?** Для навчання й розуміння роботи LINQ. Коли потрібна інша семантика: негайне виконання, інша обробка порожніх колекцій, логування, власні перевірки. Коли потрібен метод, якого в LINQ немає (`ForEach` для `IEnumerable<T>`). Під обмеженнями середовища, де LINQ недоступний або небажаний, наприклад у гарячому коді Unity, де важливі алокації.
